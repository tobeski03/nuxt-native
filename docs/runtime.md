# Native JavaScript runtime

Nuxt-native keeps rendering native. JavaScript is used for page logic, state, and event handlers, while Android views remain the rendering surface.

## Current boundary

The Android prototype embeds QuickJS through `ScriptRuntime`. The fixture generator extracts a page's `<script setup>` block, lowers JavaScript or TypeScript with esbuild, and writes a route script asset. The checked-in showcase also has `Native`, `Debug`, and `Preview` selections. Those are demo behavior presets only; they do not select the framework runtime. The actual data path is either the default embedded server or the optional remote API selected by `runtimeConfig.public.apiBase`. Both paths keep the Android view surface native.

- `ref()` state objects with a Java-to-JavaScript state-change callback; both Vue-style `ref(value)` calls inside helpers and compiler-keyed internal refs are accepted;
- common Vue ref/reactivity helpers: `shallowRef`, `reactive`, `shallowReactive`, deep cached `readonly`, `computed`, `isRef`, `unref`, `toRef`, `toRefs`, `watch`, `onWatcherCleanup`, `watchEffect`, `watchPostEffect`, `watchSyncEffect`, `nextTick`, `queuePreFlushCb`, `queueJob`, `queuePostFlushCb`, and `flushPostFlushCbs`; pre-flush callbacks run before main jobs, post-flush callbacks run afterward, and jobs queued by them are drained in the next scheduler turn;
- `$fetch()` backed by the bundled `NativeServer` route bridge by default; request options such as `method`, `body`, `headers`, `query`, and `params` cross the native boundary and become the embedded handler event's method, body, headers, and URL query. When `runtimeConfig.public.apiBase` is a non-empty HTTP(S) URL, the same bridge uses the native HTTP client instead, preserving response bodies, status codes, and response headers without changing page code;
- `$fetch.raw()` responses with serialized `body`, `status`, and `headers` metadata while ordinary `$fetch()` continues to resolve the body;
- `$fetch.create(defaults)` configured clients that merge default and per-request options, merge headers, and resolve relative paths against a configured `baseURL`; `.raw()` is available on each client too;
- native-bridged `useFetch()` results exposing `data`, `pending`, `error`, and `refresh` refs; requests execute on the embedded server executor and resolve back into the route runtime;
- `useLazyFetch()` and `useLazyAsyncData()` deferred records that remain pending until their `refresh()` method or a cache refresh helper is called;
- async-data `default`, `transform`, and `pick` options applied inside the route runtime after a handler or fetch resolves;
- async-data `watch` sources refresh records when reactive inputs change, including for `useFetch()`;
- async-data refresh generations discard stale native responses so newer route state cannot be overwritten by an older request;
- `watchEffect()` tracks native ref reads, invokes registered `onCleanup()` callbacks before reruns and on stop, and reruns on changes until its returned cleanup function is called;
- `watchEffect()` also tracks properties read from native `reactive()` objects and responds to their assignment or deletion;
- `effectScope()`, `getCurrentScope()`, and `onScopeDispose()` provide explicit reactive ownership and cleanup; non-detached scopes created during component setup are stopped with that component;
- `reactive()` uses cached deep proxies for nested objects, while `shallowReactive()` deliberately leaves nested objects unproxied;
- `watch()` supports refs, getters, reactive-object sources (including nested reactive objects inside source arrays) with deep mutation detection, source arrays, `onCleanup()` callbacks before the next callback and on stop, and the `{ immediate: true }` and `{ once: true }` options with element-wise array comparison;
- `computed()` supports getter functions and writable `{ get, set }` refs that compose with `isRef()`, `unref()`, and native watchers;
- computed getters are lazy and cached, with dependency invalidation feeding native watchers and effects;
- route-scoped `provide()`/`inject()` shares values across bundled page, layout, and component setup code without exposing native host objects;
- native lifecycle hooks include `onBeforeMount`, `onMounted`, `onBeforeUnmount`, and `onUnmounted`, with before hooks ordered around route and component teardown;
- async-data `error` refs preserve structured failure metadata (`message`, `status`, `statusMessage`, `data`, and `headers`) from native server responses;
- synchronous `useAsyncData()` for local handlers, preserving the same result shape and deduplicating identical keys within a route runtime;
- `refreshNuxtData()` and `clearNuxtData()` for route-runtime async-data refresh and cache invalidation;
- an embedded Promise-compatible continuation layer with a framework-owned job queue; async functions are lowered to ES2015 generators, native bridge completions drain queued handlers deterministically, and the runtime does not claim to expose QuickJS's unavailable pending-job executor;
- route-scoped `onMounted()` and `onUnmounted()` callback registries invoked by the native router;
- `useRoute()` returns a stable native route object whose fields read the current router snapshot, while `navigateTo()` and `useRouter()` accept route-location objects with encoded query arrays and hash fragments;
- Nuxt-shaped route snapshots with decoded dynamic params, query values, and hash fragments;
- generated `reactive()`, `computed()`, `watch()`, and `watchEffect()` primitives for page logic;
- keyed `useState()` refs that share identity within a route runtime, participate in native state snapshots, and persist through the reserved native-storage namespace when the `storage` capability is available;
- persistent `useCookie()` refs backed by app-scoped native storage, with an in-memory fallback when the storage capability is unavailable;
- `useRuntimeConfig()`, `useAppConfig()`, `useError()`, `showError()`, `clearError()`, and `definePageMeta()` authoring shims, with public runtime configuration, static app configuration, and native route-error recovery supplied by the host;
- conventional `app.config.ts`, `app.config.js`, and `app.config.mjs` files are loaded into `useAppConfig()`; explicit `nuxt-native.config.json` values override matching keys;
- conventional `nuxt.config.ts`, `nuxt.config.js`, and `nuxt.config.mjs` files contribute static `runtimeConfig.public` and `appConfig` values before native configuration overrides are applied;
- `useHead()` and `useSeoMeta()` metadata composables; title metadata is applied to the host Android activity through the native state bridge;
- capability-gated native service composables: `useNativeDevice()` reads Android device/package metadata, `useNativeStorage()` maps JSON values to app-scoped `SharedPreferences`, and `useNativeClipboard()` reads/writes text through Android `ClipboardManager`;
- `useNativePermissions()` with Android `checkSelfPermission` checks and asynchronous `requestPermissions` results routed back to the active QuickJS runtime;
- `useNativeFileSystem()` backed by the app-private Android `filesDir`, with traversal protection and text/list operations;
- `useNativeNotifications()` backed by Android `NotificationManager` and notification channels, with Android 13+ permission checks;
- `useNativeMedia()` backed by Android's `ACTION_OPEN_DOCUMENT` picker and `MediaStore` camera capture, resolving persisted content URIs into the originating route runtime;
- `useNativeDialog()` backed by an Android `AlertDialog`, with Promise results delivered back to the originating route runtime;
- `useNativeAppLifecycle()` with an active/background ref and unsubscribe-able change listeners driven by Android activity lifecycle callbacks;
- `useNativeSensors()` backed by Android `SensorManager` for accelerometer, gyroscope, magnetometer, and rotation-vector subscriptions;

- page-scoped `onBeforeRouteLeave()` and `onBeforeRouteUpdate()` guards evaluated by the active route runtime before native navigation;

- native `KeepAlive` subtree caching during structural reconciliation;

- an optional `app/error.vue` or root-level `error.vue` native error surface receiving an `error` object; its `<script setup>` is packaged as a dedicated error runtime so actions such as `clearError()` remain live on the recovery screen, with a framework-owned retry action retained when the custom surface cannot render;
- native template text expressions support common fallback forms such as optional property access and logical-or defaults, so idiomatic Nuxt interpolations remain readable on the Android surface;
- startup plugins with capability checks, serializable `nuxtApp.provide()` values, object/function plugin forms, bundled relative JavaScript/TypeScript imports, hook dispatch, and deterministic disposal;

- generated `server/middleware` assets that run before embedded API handlers;
- direct native invocation of declared page functions by validated identifier;
- a generated snapshot function for refs declared in the page.
- a generated snapshot function for refs and serializable top-level setup bindings used by native template expressions; functions, Promises, and circular values are excluded so helper objects do not leak into the renderer;
- native `conditional` and `for` control nodes driven by hydrated route state, including initial ref values and later structural rerenders;
- runtime `:style`, inline style, and `:class` binding refreshes for supported native properties;
- static Tailwind responsive (`sm:` through `2xl:`) and system-theme (`dark:`/`light:`) style variants selected by the native Android configuration;
- native image loading for packaged public assets, content/file/resource URIs, data URLs, and HTTPS sources, plus internal anchor navigation;
- Android accessibility semantics for labels, descriptions, roles, headings, hidden/disabled state, live regions, and focusability;

Each script also emits a JSON manifest listing its declared actions and state refs. The Android route host uses that manifest to reject undeclared event calls.

Native text inputs attach a `TextWatcher` for `v-model` and write the edited value back into the active QuickJS ref object. Select controls do the same through `Spinner`, and range inputs use `SeekBar` with integer `min`, `max`, and `step` mapping. Native controls also support `@input` and `@change` handlers with `{ type, value }` event payloads, whether or not `v-model` is present. All controls receive initial state and later state-driven refreshes without feeding programmatic updates back into the ref. Ref setters notify registered watchers and the Android host, which refreshes bound native text and disabled states; dynamic disabled values are also applied during the initial native view creation. Refreshes do not rewrite `EditText` contents, preventing programmatic repaint from echoing through `v-model` indefinitely. This keeps the data path aligned with Vue authoring: native controls are the platform surface, while page state remains JavaScript state.

The Android host can therefore invoke a page action without a Java branch for each application-specific action. Page JavaScript is confined to a single QuickJS worker, while state notifications are marshalled back to Android's main thread. Route entry invokes mounted callbacks and route replacement invokes unmounted callbacks before the old runtime is closed. `useFetch()` now returns immediately with `pending: true`; the embedded server request runs asynchronously and resolves the route's `data`, `error`, and `pending` refs on the same QuickJS worker. Async page functions lowered by esbuild resume through the same bridge when `$fetch()` settles.

The native router persists its route history and active index in app-private `SharedPreferences`. It also persists the declared page state refs for each route under a route-specific key. On activity recreation or process restoration it validates every saved path against the generated route manifest, restores the active screen and its serializable page state before the first native snapshot, and discards corrupt or invalid state safely. Route, middleware, plugin, and action failures are contained in a native retry screen; startup failures use the same recovery surface instead of escaping as an uncaught activity exception. The CLI accepts `NUXT_NATIVE_ANDROID_SDK`, `NUXT_NATIVE_ADB`, and `NUXT_NATIVE_GRADLE` as stable machine-level tool overrides, while command flags remain the highest-precedence option.

## Deliberate limits of this first runtime slice

This is not yet the full Vue/Nuxt runtime. It does not currently implement Vue's complete scheduler semantics, server hydration, or the complete Nitro compatibility surface. The embedded runtime does provide a deterministic framework-owned Promise continuation queue, but it is not the JavaScript engine's native pending-job executor. Component setup is supported for direct refs, handlers, effect scopes, and teardown ownership, while complete Vue scheduler and hydration semantics remain separate runtime layers before calling the framework production-ready.

The current asset is pinned to `app.cash.quickjs:quickjs-android:0.9.2` and is vendored under `android/app/libs` so offline Android builds remain reproducible. The dependency provides the JavaScript engine; it does not turn browser APIs into native APIs automatically. Because this version does not expose QuickJS's pending-job executor, generated page scripts use a framework-owned Promise-compatible continuation layer rather than claiming to expose the engine's native microtask queue.

Component setup is currently bundled into the owning page runtime. Direct `ref()` declarations, serializable non-ref setup bindings, `defineModel()`, `useFetch()`/`useAsyncData()` state, native state write-back, function handlers, and component-scoped `onMounted()`/`onUnmounted()` callbacks are supported; template bindings are rewritten to instance-scoped keys such as `__nuxtComponent0_count`, `__nuxtComponent0_device`, and `__nuxtComponent0_data`, while event handlers use names such as `__nuxtComponent0_increment`. A generated state-binding registry routes native `v-model` updates back to the correct component ref, and a component model ref synchronizes updates to its parent expression. This preserves independent component state without creating a second renderer.
Component `watch()` and `watchEffect()` registrations created during setup are tracked by the component scope and stopped during native unmount, including the watchers installed by component-scoped async-data and model helpers. Component app-lifecycle listeners and sensor subscriptions are also disposed with the component. Reactive registrations created later from arbitrary asynchronous callbacks remain subject to the route runtime's lifecycle unless the callback uses an explicit `effectScope()` and `onScopeDispose()` boundary.

Conditional, suspense, and dynamic-component nodes now retain their native view when the selected branch/content is unchanged and replace only the affected subtree when the selector changes. `v-for` nodes with `:key` (or index fallback when no key is supplied) preserve item containers, reorder them by key, and refresh their bound children in place. Array loops and object loops (`(value, key) in record`) preserve the expected value/key bindings; object keys are normalized deterministically before native reconciliation. Each repeated item owns cloned structural node identities, so nested conditionals and dynamic components reconcile independently instead of sharing a view lookup across loop iterations. Unsupported deep cases still fall back to safe item reconstruction until the renderer gains a complete component-level diff algorithm.

Route middleware is compiled under `assets/middleware/` and indexed by `middleware.json`. The native router evaluates each guard before rendering a target route. Middleware is deliberately isolated from the destination page runtime, so a rejected or redirected transition cannot partially mount the destination screen.

Route and page-action failures are contained by the native host. Pages and components can register `onErrorCaptured()` handlers; when one returns `false`, the error is considered handled and the active route remains mounted so the handler can update local state. Unhandled failures unmount the active runtime, render `app/error.vue` or root-level `error.vue` when present with an `error` object containing status and message fields, and expose a retry action for the last requested path. Render-time subtree failures can instead be handled by `NuxtErrorBoundary` when its fallback slot is present.

Startup plugins are indexed by `plugins.json`, evaluated before the initial route, and isolated in their own QuickJS runtime. Capability checks are resolved from a host-owned allowlist, while provided values cross into page runtimes as JSON snapshots through `useNuxtApp()`. The host dispatches `app:mounted` once after the first native route commits, forwards `app:state` on active/background transitions, and invokes `app:dispose` before closing the plugin runtime.

Native service bridges are injected into every route, plugin, and middleware runtime. A host-owned `NativeCapabilityBroker` supplies one policy snapshot to all of them; it is the single source of truth for which named services are available. The device bridge returns a JSON snapshot, the storage bridge accepts only string keys and serialized JSON values, the filesystem bridge confines text operations to the app-private files directory, the notifications bridge owns Android channels and posting, the dialog bridge maps to `AlertDialog`, and the media bridge owns document-picker and `MediaStore` camera activity results; this keeps Android objects outside JavaScript and makes the same generated script safe to test with no-op bridges. Asynchronous dialog, permission, and media results retain the originating route runtime; if navigation replaces that runtime first, the late result is ignored safely. `useNativePermissions()` delegates to the Android activity for declared runtime permissions and resolves the result back into the originating route runtime. A host can withhold a capability, in which case native services report unavailable rather than pretending to work.

When a route runtime is unmounted, the host releases its pending fetch, permission, dialog, media, and sensor ownership records. Late callbacks are therefore ignored, pending camera output is cleaned up, and sensor listeners are unregistered instead of retaining an obsolete page runtime.

Server handlers are compiled and packaged separately under `assets/server/` with a `server-routes.json` manifest. Asset paths preserve the source directory structure, so same-named handlers in different server folders cannot overwrite each other; duplicate method/path definitions fail the build with both source files named. `server/middleware` is emitted into its own `server-middleware.json` manifest and runs against the same request event before the selected handler. `server/plugins` is emitted into `server-plugins.json`; each function- or object-style `defineNitroPlugin()` module initializes inside each embedded request context and may register `request`, `beforeResponse`, or `afterResponse` hooks. Request hooks can enrich the event or return `false` to abort before middleware and route dispatch; response hooks receive the event with the serialized native response. Exceptions thrown by plugin hooks now preserve `statusCode`, `statusMessage`, `message`, and `data` as a structured native error instead of disappearing into a successful response. Plugin globals are request-scoped, so mutable state cannot leak between native requests. The event includes method, URL/path, body, query, headers, and decoded dynamic route `params`; inbound header names are normalized to lowercase for case-insensitive `getHeader()` access, and repeated query keys are exposed as arrays. Handlers can use `isMethod()`/`assertMethod()` for Nitro-style method guards, `readValidatedBody()`/`getValidatedQuery()` for synchronous or Promise-returning validation, and `sendError()` to serialize structured status, message, and data bodies. They can read request headers with `getRequestHeader()`/`getRequestHeaders()`, compose responses with `setHeader()`, `setResponseHeaders()`, `appendResponseHeader()`, `getResponseHeader()`, `removeResponseHeader()`, and `getResponseStatus()`, explicitly finalize bodies with `send()`/`sendNoContent()`, or issue a native `sendRedirect()` response with a `Location` header and status. Explicit response bodies take precedence over a handler return value at the native boundary. Handlers can set response metadata or throw `createError()` failures. Embedded handlers also support `getCookie()`, `setCookie()`, and `deleteCookie()`: request cookies are parsed from the native event's `cookie` header, while response cookies are emitted as repeated `set-cookie` values with standard path, expiry, max-age, same-site, secure, and HTTP-only attributes. These are app-local embedded request semantics; remote API cookies remain controlled by the remote HTTP boundary. Each embedded request now receives a fresh QuickJS context, so middleware globals, handler globals, plugin globals, and mutations cannot leak into another request; asynchronous requests remain serialized through the native server executor. Missing routes, middleware aborts, handler errors, and malformed server execution now produce structured native error responses. Async server handlers are lowered to generators and settled through a framework-owned Promise queue before the native response is serialized; genuinely external asynchronous work still requires a host bridge. Embedded request headers remain app-local, while remote forwarding is available through `runtimeConfig.public.apiBase`.

Modules under `server/utils` are compiled into the same embedded route and middleware assets as convention auto-imports. Utility exports are available without local imports, and relative JavaScript/TypeScript imports are bundled into the asset before it reaches QuickJS; project-resolvable pure-JavaScript npm packages can also be bundled into page and component setup. Packages that require browser globals, Node built-ins, native bindings, or other unavailable host services remain outside the supported packaged boundary. Duplicate exported utility names are build errors.

## Next runtime milestones

Remote API mode is selected by `runtimeConfig.public.apiBase`. The Android host uses native `HttpURLConnection` for that boundary, forwards request headers and JSON bodies, decodes JSON or text responses, preserves status, status text, and response headers for `$fetch.raw()` (including repeated header values joined in wire order), and converts HTTP status failures into the same `$fetch()` error shape used by embedded handlers. No WebView or browser fetch implementation is introduced.

The checked-in showcase exercises both integration boundaries. Its page imports the pure-JavaScript `clsx` npm package, which is bundled into the route asset and displayed as `native npm module`. When `runtimeConfig.public.apiBase` is set, the same page switches its profile request to `/users/1` and displays the remote response; the default project configuration leaves the embedded server path active. A live handset smoke test used `https://dummyjson.com/users/1` and verified the returned `Emily Johnson` payload, `External API: connected`, the bundled npm-module result, and zero native runtime errors. The external endpoint is test coverage, not a framework dependency.

1. Extend asynchronous navigation cancellation to any future host-owned hooks; page-scoped route guards and route middleware now share a transaction token, so stale Promise completions and synchronous failures cannot replace or report over a newer navigation.
2. Expand the server bridge with richer errors, remote deployment modes, and production Nitro compatibility.
3. Expand the script compiler beyond setup-owned effect scopes to complete Vue scheduler semantics and the remaining compiler macro edge cases.
4. Add plugin contexts with explicit native capability permissions and lifecycle disposal.
5. Replace the compatibility continuation layer with true QuickJS Promise-job scheduling when the engine binding exposes a supported executor. The Android host now probes for a future `executePendingJobs()` binding method and invokes it when available, while retaining the framework-owned queue as the verified fallback. The bundled QuickJS Android 0.9.2 binding currently exposes `evaluate()`/`execute()` but no pending-job executor, so this host continues to use the fallback path.
## Showcase runtime modes

The example app's runtime selector is an app-level demonstration of different behaviors; it does not switch the underlying Android renderer.

- `Native` keeps live embedded-server data and native actions enabled.
- `Debug` adds visible bridge and server diagnostics to the page.
- `Preview` keeps profile edits local to the screen and skips the server write.

The selected mode is persisted through `useNativeStorage()` under `showcase-mode`. Framework applications may use the same pattern for their own development or presentation profiles.

Action state is synchronized in two layers: reactive setters stream individual
changes to the renderer, while the host applies a complete runtime snapshot
after an action and after an asynchronous server bridge response. The snapshot
is a timing-safe boundary for Promise-based handlers such as form saves, so a
native view cannot remain stuck on an intermediate label when the JavaScript
continuation has already completed.

The native select control is reconciled after state updates, so its visible selection remains aligned with the reactive value that drives the page.

Application plugins can declare a host capability allow-list with `capabilities: ['device', 'storage']`. Their `nuxtApp.capabilities` contains only declared capabilities that the Android host actually grants, and `nuxtApp.hasCapability(name)` provides the corresponding guard. Plugins may register teardown with `nuxtApp.onDispose(callback)` or return a disposer from `setup`; teardown runs in reverse registration order before the plugin context is discarded. This keeps native capability access explicit and prevents plugin listeners from surviving a runtime lifecycle.

The showcase also includes a `flex-row overflow-x-auto` capability rail. It is an integration fixture for nested native horizontal scrolling, so a handset check can validate both the root vertical `ScrollView` and an inner `HorizontalScrollView` from ordinary Nuxt/Tailwind markup. Reactive reconciliation preserves the horizontal scroll container as a structural boundary, keeping each card's content aligned after server data or state updates.

The showcase home route intentionally includes content below the first viewport to exercise the generated root `ScrollView` on a handset. Its native API matrix also makes the scroll range substantial enough to validate a real upward swipe, rather than relying on content that merely touches the viewport edge. It also uses `grid grid-cols-2` for its runtime/data cards, exercising equal-width native grid cells in the actual app. The root scroll surface keeps its scrollbar visible, enables nested scrolling and Android overscroll feedback, and uses smooth scrolling so overflow is discoverable during a short swipe. This is an integration fixture for overflow, touch scrolling, nested cards, and bottom-of-page navigation—not just a static visual sample. A device check should confirm that the lower capability cards, API matrix, and route actions become reachable after an upward swipe.

The `/settings` showcase route includes a native form boundary with a required email field, readonly `v-model`, focus/blur handlers, keyboard events, and `@submit.prevent`, plus a clipboard card that exercises Android text read/write through `useNativeClipboard()`. It is an end-to-end fixture for validating Android control and capability semantics through ordinary Nuxt markup.
